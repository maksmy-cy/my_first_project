1. Три основные области работы с файлами в Git и их отличия
В Git файл проходит три области:

Область	Что это	Назначение
Рабочая папка (Working Directory)	Файлы на диске, которые вы реально видите и редактируете	Здесь вы создаёте и изменяете файлы
Индекс (Staging Area / Index)	Промежуточная область, куда попадают изменения после git add	Позволяет выбрать, какие именно изменения попадут в следующий коммит
Репозиторий (Repository / .git)	Хранилище всех зафиксированных версий (коммитов)	Содержит полную историю проекта
Отличия:

В рабочей папке изменения ещё «черновые» — Git их видит, но не сохраняет.

В индексе изменения подготовлены к коммиту, но ещё не зафиксированы.

В репозитории изменения сохранены навсегда (как версия) и имеют хеш коммита.

Схема: Working Directory → git add → Staging Area → git commit → Repository

2. Что происходит при выполнении команд git add, git commit, git push
git add <файл> — добавляет изменения из рабочей папки в индекс (staging area). Файл становится «подготовленным» к коммиту. Сам коммит ещё не создаётся.

git commit -m "сообщение" — фиксирует всё, что лежит в индексе, в локальном репозитории. Создаётся новый коммит с уникальным хешем (SHA-1), автором, датой и сообщением. Изменения теперь в истории проекта, но только локально.

git push — отправляет локальные коммиты в удалённый репозиторий (например, на GitHub). Только после этого изменения становятся доступны другим людям и видны в веб-интерфейсе GitHub.

Кратко: add → подготовить, commit → сохранить локально, push → отправить на сервер.

3. Почему важно писать информативные сообщения к коммитам
Информативное сообщение к коммиту:

Объясняет, что и зачем изменено — через месяц вы (или коллега) поймёте суть правки без чтения кода.

Упрощает поиск — можно найти нужный коммит по ключевому слову через git log --grep.

Помогает в code review — ревьюер быстрее понимает логику изменений.

Позволяет откатить конкретное изменение — понятно, какой коммит за что отвечает.

Формирует историю проекта — по git log можно восстановить хронологию разработки.

Сообщения вроде update, fix, исправление бесполезны: они не несут смысла и не отличают один коммит от другого.

Хороший пример: Добавлена валидация email в форме регистрации
Плохой пример: update

4. Чем отличается git add имя_файла от git add .
git add имя_файла — добавляет в индекс только указанный файл (или несколько, если перечислить их через пробел).

git add . — добавляет в индекс все изменения во всех файлах текущей директории и поддиректорий: новые файлы, изменённые, удалённые.

Когда что использовать:

Ситуация	Команда
Нужно закоммитить только один конкретный файл	git add имя_файла
Нужно закоммитить все изменения сразу	git add .
В папке есть файлы, которые не должны попасть в коммит (черновики, логи)	git add имя_файла — точечно
Уверены, что все текущие изменения логически связаны	git add .
Важно: перед git add . всегда проверяйте git status, чтобы случайно не добавить лишнее (например, временные файлы, пароли, .DS_Store на macOS).

5. Что показывает git status и как меняется её вывод
git status показывает текущее состояние рабочей папки и индекса:

На какой ветке вы находитесь.

Какие файлы изменены, но ещё не добавлены в индекс.

Какие файлы добавлены в индекс и готовы к коммиту.

Какие файлы не отслеживаются (untracked) — Git их ещё не знает.

Есть ли конфликты или незавершённые операции (merge, rebase).

Как меняется вывод на разных этапах:

Сразу после git init: nothing to commit (create/copy files and use "git add" to track) — пустой репозиторий.

После создания нового файла: файл в разделе Untracked files — Git его видит, но не отслеживает.

После git add: файл в разделе Changes to be committed — готов к коммиту.

После изменения уже отслеживаемого файла (без add): файл в разделе Changes not staged for commit — изменения есть, но в индекс не попали.

После git commit: nothing to commit, working tree clean — всё зафиксировано.

6. Для чего нужна команда git remote add origin URL и что означает «origin»
git remote add origin URL — добавляет в локальный репозиторий ссылку на удалённый репозиторий. После этого Git знает, куда отправлять (push) и откуда забирать (pull) изменения.

remote — команда для работы с удалёнными репозиториями.

add — добавить новый удалённый репозиторий.

origin — это имя (псевдоним) удалённого репозитория. Технически можно назвать как угодно (github, upstream), но origin — общепринятое соглашение для «основного» удалённого репозитория.

URL — адрес репозитория на GitHub/GitLab.

Проверить список удалённых репозиториев: git remote -v.

Слово «origin» не является магическим — это просто удобное имя, которое по умолчанию используется в примерах и документации. Один локальный репозиторий может иметь несколько удалённых (например, origin — свой форк, upstream — оригинал).

7. Зачем нужен флаг -u в команде git push -u origin main
Флаг -u (сокращение от --set-upstream) связывает локальную ветку с удалённой. После первой отправки:

bash
git push -u origin main
Git запоминает, что локальная ветка main соответствует удалённой origin/main. В дальнейшем можно писать просто:

bash
git push
git pull
без указания origin main — Git сам поймёт, куда отправлять и откуда забирать.

Без -u при каждом push/pull пришлось бы явно указывать удалённый репозиторий и ветку.

Итого: -u = «запомни это соответствие для будущих команд».

8. Что такое ветка по умолчанию и какая создалась у вас (main или master)
Ветка (branch) — это независимая линия разработки. По умолчанию в Git создаётся одна основная ветка, в которой ведётся работа.

Исторически:

Раньше Git по умолчанию создавал ветку master.

С 2020 года GitHub и многие другие платформы перешли на main как более нейтральное название.

В современных версиях Git (2.28+) можно настроить имя по умолчанию:

bash
git config --global init.defaultBranch main
У меня создалась ветка: main (или master, если Git старый и настройка не менялась — в задании указано проверить через git branch и при необходимости переименовать через git branch -M main).

Почему это важно:

GitHub ожидает main — если отправить master, может потребоваться переименование или настройка.

Имя основной ветки влияет на CI/CD, деплой, настройки репозитория.

Единообразие упрощает работу в команде и переход между проектами.

9. Как просмотреть историю коммитов и какую информацию она показывает
Команда:

bash
git log
Что показывает для каждого коммита:

Хеш (SHA-1) — уникальный идентификатор коммита (например, a1b2c3d...).

Автор — имя и email из настроек Git.

Дата и время коммита.

Сообщение коммита (то, что вы писали после -m).

Полезные варианты:

git log --oneline — краткий формат: хеш + сообщение (удобно для быстрого просмотра).

git log --graph --oneline --all — дерево веток и коммитов.

git log -p — с полным diff (что именно изменилось).

git log --stat — со статистикой изменённых файлов.

git log --author="Имя" — фильтр по автору.

git log --grep="слово" — поиск по сообщению коммита.

Пример вывода git log --oneline:

text
a1b2c3d Дополнен README файл
e4f5g6h Добавлено изменение в main.txt
i7j8k9l Добавлен главный файл проекта
10. Что произойдёт, если сделать изменения в файле, но не выполнить git add перед git commit
Ничего не закоммитится. Коммит создаётся только из того, что лежит в индексе (staging area). Если файл изменён, но не добавлен через git add, его изменения:

останутся в рабочей папке — файл на диске будет содержать новые данные;

не попадут в индекс — Git будет считать их «не подготовленными»;

не войдут в коммит — в истории сохранится предыдущая версия файла.

Что покажет git status:

text
Changes not staged for commit:
  modified:   main.txt
Что произойдёт при git commit:

Если в индексе есть другие файлы — закоммитятся только они.

Если индекс пуст — Git выдаст сообщение:

text
no changes added to commit (use "git add" and/or "git commit -a")
Как исправить:

Добавить файл и закоммитить заново:

bash
git add main.txt
git commit -m "..."
Или закоммитить все изменения в отслеживаемых файлах одной командой (без предварительного add):

bash
git commit -am "сообщение"
⚠️ Флаг -a добавляет только уже отслеживаемые файлы. Новые (untracked) файлы он не захватит — их всё равно нужно git add.

Вывод: git add — обязательный шаг перед git commit, если вы хотите зафиксировать конкретные изменения.

Как оформить в answers.md
Скопируйте ответы в файл answers.md, например:

bash
nano answers.md
Вставьте текст, сохраните (Ctrl + O → Enter → Ctrl + X), затем:

bash
git add answers.md
git commit -m "Добавлены ответы на вопросы самоконтроля"
git push
После этого ссылка на репозиторий готова к сдаче. ✅
